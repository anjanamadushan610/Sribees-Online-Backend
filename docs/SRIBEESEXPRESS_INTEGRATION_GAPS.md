We read the contract end to end and mapped it against a live grocery
checkout. **The core flow fits** — rates → book → track → cancel → webhook is

smaller gaps. In priority order:

## 1. BLOCKER — handover verification code (the COD problem)

### Why we need it

On a **COD** order the rider collects real cash (routinely LKR 3,000–15,000
for a grocery basket) and hands over a parcel. Today the contract gives us
exactly one signal that this happened: a `delivered` status on a webhook.
That is a claim made by your side with nothing tying it to the actual
customer. If a customer says "I never got it" we have no evidence, and the
dispute lands on us because we are the merchant of record.

Your earlier `/client-portal/api/*` contract had this (its §15). The new
contract dropped it. We need it back.

### What we want to build

1. Customer places a COD order in the SRIBEESonline app.
2. Our backend generates a short numeric **handover code** and displays it in
   the app on the order screen (we already do exactly this for prepaid
   orders — the UI exists).
3. Rider arrives, collects the cash, and **before releasing the parcel** asks
   the customer to read out the code and enters it in the rider app.
4. The code is checked. Match → parcel released, shipment goes `delivered`.
   No match → parcel not released, shipment goes `failed`.
5. We receive confirmation that the code was verified, and store it as proof.

The same mechanism should apply to **prepaid** orders too (proof of correct
recipient), but COD is what's blocking us.

### Option A — we hand you the code at booking (**our recommendation**)

Least work for both sides, and it fits your existing architecture with no new
inbound-call concept.

**Add to `POST /ecommerce/shipments` request:**

```json
{
  "merchant_order_ref": "FC-20260828-A7K2M9",
  "quote_id": "qt_...",
  "recipient_name": "A. Perera",
  "recipient_phone": "+94771234567",
  "recipient_address": "12 Galle Road, Colombo 03",
  "cod_amount": 4820.00,

  "handover_code": "4821",
  "handover_code_required": true
}
```

| Field | Type | Notes |
|---|---|---|
| `handover_code` | string, 4–6 digits, optional | Generated by us, unique per shipment. Store it against the shipment; the rider app validates against it. |
| `handover_code_required` | bool, default `false` | When `true`, the rider **must not** mark the shipment `delivered` without a matching code. |

**Rules we're asking you to enforce:**

- Attempt-limited: **5 wrong entries**, then the code locks and the shipment
  can only go `failed` (reason `handover_code_failed`, see §5) — this stops a
  rider brute-forcing a 4-digit code at the door.
- Constant-time comparison, and never show or echo the code back in any API
  response, tracking page, or rider-visible screen **before** it is entered.
  The rider must not be able to read the code off their own app — that
  defeats the entire mechanism. The rider app should only ever receive a
  match/no-match answer from your server.
- The code is not a secret with long-term value, but treat it as one for the
  lifetime of the shipment.

**Add to the `delivered` webhook payload** (and to `GET /ecommerce/shipments/{id}`):

```json
{
  "event": "shipment.status_changed",
  "event_id": "b3f1c2a4-...",
  "shipment_id": "SXP0000012345",
  "status": "delivered",
  "at": "2026-08-28T15:02:00+05:30",
  "handover": {
    "code_verified": true,
    "verified_at": "2026-08-28T15:01:44+05:30",
    "attempts": 1
  },
  "cod": {
    "collected": true,
    "amount": 4820.00,
    "collected_at": "2026-08-28T15:01:44+05:30"
  }
}
```

The `cod` block is what closes the loop on §3 at the per-shipment level.
Please send it on every COD shipment's `delivered` event, and send
`"collected": false` with a reason if the parcel was delivered but the cash
was not — we'd rather know.

### Option B — you call us to verify

If you'd prefer the code never leaves our system, we already run this
endpoint and can keep it:

```http
POST https://<our-origin>/api/v1/courier/webhooks/orders/{merchant_order_ref}/delivery-code/confirm
Content-Type: application/json
```
```json
{ "waybill_number": "SXP0000012345", "code": "4821" }
```
```json
{ "success": true, "message": "Code confirmed." }
```

We enforce the 5-attempt limit and constant-time compare on our side. The
rider app calls your server, your server calls this, and only on
`success: true` does the rider release the parcel.

This needs authentication. Rather than yet another shared key, the cleanest
fit with your existing design: **let us register a "handover verification
URL" alongside our webhook endpoint** (`POST /ecommerce/webhook-endpoints`)
and sign the call with the **same** `X-Sribees-Signature`
(`t=<unix>,v1=<hmac-sha256 of "{t}.{raw_body}">`) scheme from §10.3. We are
already implementing verification for that scheme.

The trade-off is a synchronous network call standing between the rider and
releasing a parcel — if we're down, deliveries stall. **Option A degrades
better**, which is why we prefer it. Your call.

### Either way, please confirm

- [ ] Which option you'll implement
- [ ] Code length you'll support (we default to 4 digits; we can do 6)
- [ ] What the rider app shows the customer when the code doesn't match
- [ ] Whether a rider can override or skip the code, and if so who authorises
      it — we'd want that logged and surfaced to us

## 2. BLOCKER — pickup location for a multi-branch merchant

The contract has `origin_branch_id` on `POST /ecommerce/rates`, described as
*"Accepted and passed through to the eventual booking; does not currently
affect the price."* That's the only origin-shaped field anywhere in the
contract, and it isn't on `POST /ecommerce/shipments` at all.

**Our situation:** SRIBEESonline is multi-branch. Each order is fulfilled from
a specific physical grocery branch (we resolve the branch from the customer's
post office at checkout), and the rider must collect the parcel from **that
branch's address**, not from one fixed warehouse. Two orders placed in the
same minute can have different pickup points.

**Questions:**

1. Where does SribeesExpress currently get the pickup address from — a single
   address configured on our API-key account?
2. Is `origin_branch_id` **your** branch id or **ours**? If yours, we need a
   list endpoint or a mapping — we have no way to obtain those ids today.

**What we need**, in rough order of preference:

- **(a)** A merchant-managed pickup-location registry:
  `POST` / `GET /ecommerce/pickup-locations` (name, contact phone, full
  address, post office/district/province, optional lat/lng), returning an id
  we then send as `pickup_location_id` on `POST /ecommerce/shipments`. This is
  the right long-term shape — pickup points are stable, orders reference them.
- **(b)** Failing that, accept an inline pickup block on
  `POST /ecommerce/shipments`:
  `{ "pickup": { "name": ..., "phone": ..., "address": ..., "post_office": ..., "district": ..., "province": ... } }`
- **(c)** At absolute minimum, tell us how to configure more than one pickup
  address per account, even if it's a manual ops process.

Without one of these, every parcel routes to whatever single address is on
file and our other branches cannot ship at all.

## 3. BLOCKER — COD remittance / settlement

You collect our customers' cash. The contract has no endpoint that tells us
when that money comes back to us, or which shipments a payout covers. Right
now the only COD data we ever see is the `cod_amount` we sent you.

We need to reconcile "cash collected" against "cash received in our bank
account" — an accounting requirement, not a nice-to-have.

**Requested:**

```http
GET /ecommerce/remittances?from=2026-08-01&to=2026-08-31&limit=&offset=
```
```json
[
  {
    "remittance_id": "RMT000123",
    "status": "paid",
    "paid_at": "2026-08-27T10:00:00+05:30",
    "gross_cod_collected": 184300.00,
    "delivery_charges_deducted": 12400.00,
    "commission_deducted": 0.00,
    "net_paid": 171900.00,
    "bank_reference": "CEFT-88213",
    "shipment_count": 41
  }
]
```

```http
GET /ecommerce/remittances/{remittance_id}/shipments
```
→ the per-shipment breakdown (`shipment_id`, `merchant_order_ref`,
`cod_collected`, `delivery_charge`, `net`).

Plus, on `GET /ecommerce/shipments/{id}`, a `remittance_id` field (null until
settled) so we can answer "has this order's cash been paid to us?" without a
date-range scan.

Also please document, even in prose: **the remittance cycle** (daily? weekly?
T+n?), what gets deducted, and what happens to COD cash on a `returned`
shipment.

A `remittance.paid` webhook event would be welcome but is not required — we
can poll this daily.

## 4. Delivery slot (date + time window)

Groceries are scheduled purchases. Our orders already carry
`delivery_slot_date` and `delivery_slot_time` — the customer picks them at
checkout and we show them the commitment. The contract has nowhere to send
them, so today we would be promising a slot we have no mechanism to honour.

**Requested on `POST /ecommerce/shipments`:**

```json
{
  "requested_delivery_date": "2026-08-29",
  "requested_delivery_window": "09:00-12:00"
}
```

Best-effort is fine — we understand you may not be able to guarantee windows.
Even just carrying it through to the rider's job card, so they know the
customer expects a morning delivery, is most of the value. If you can also
return a `promised_delivery_date` on the shipment, we'll show that instead of
our own guess.

Related: on `POST /ecommerce/rates`, an optional `service_level` field
(`standard` / `express` / `same_day`) with the difference reflected in
`amount_lkr`. Same-day grocery delivery is a product we want to sell; today we
have no way to price it.

## 5. Failure reason on `failed` and `returned`

The status vocabulary has `failed` and `returned` but no reason. For groceries
a failed delivery is expensive — perishables spoil, and we have to decide
within minutes whether to refund, re-dispatch, or write off. "Failed" alone
doesn't let us decide, and doesn't let us tell the customer anything useful.

**Requested — add to the webhook payload and `GET /ecommerce/shipments/{id}`:**

```json
{
  "status": "failed",
  "failure_reason": "customer_unreachable",
  "failure_note": "Called 3 times, no answer",
  "attempt_number": 1,
  "next_attempt_at": "2026-08-29T10:00:00+05:30"
}
```

A stable enum, e.g.: `customer_unreachable` · `address_not_found` ·
`customer_refused` · `payment_refused` (COD, customer wouldn't pay) ·
`handover_code_failed` (see §1) · `damaged` · `rescheduled_by_customer` ·
`out_of_coverage` · `other`.

Also: **how many delivery attempts** do you make before a shipment becomes
`returned`, and can we influence that per shipment? For perishables we would
often rather have one attempt and an immediate return than a parcel sitting in
a van for two days.

## 6. Webhook reliability and a way to poll

§10.4 is honest and we appreciate it, but "no automatic retry" plus "a status
that changes only once (e.g. straight to `delivered`) will not be resent" is a
hard combination for us: `delivered` on a COD order is the single most
important event in the whole integration, and it is exactly the one your own
doc says can be silently lost.

We will implement the recommended polling fallback regardless. Two requests:

1. **Add retries.** Even a modest exponential backoff (e.g. 5 attempts over
   ~30 minutes) removes almost all of this risk. A dead-letter view in the
   existing delivery log (`GET /ecommerce/webhook-endpoints/{id}/deliveries`)
   would let us re-drive failures ourselves.
2. **Give us a list endpoint for reconciliation polling.** Right now the only
   read is `GET /ecommerce/shipments/{id}` — one shipment per call. Polling
   500 open shipments means 500 requests against a 60/min limit (§10), which
   is not viable. We need:

```http
GET /ecommerce/shipments?updated_since=2026-08-28T09:00:00Z&status=&limit=&offset=
```

returning the same objects as the single-shipment read. This one endpoint is
what makes §10.4's own "poll as a fallback" recommendation actually
implementable — without it, that advice can't be followed at our volume.

A manual
`POST /ecommerce/webhook-endpoints/{id}/deliveries/{delivery_id}/replay`
would also be handy for support, but the list endpoint matters much more.

## 7. Perishable / cold-chain flag

A grocery parcel can contain frozen, chilled, or fragile goods. There is
currently no way to tell you. At minimum we'd like a hint that reaches the
rider:

```json
{ "handling": ["perishable", "fragile", "keep_upright"] }
```

on `POST /ecommerce/shipments`. If any of these carry a surcharge, they'd need
to be accepted on `POST /ecommerce/rates` too so the quote stays correct.

Please tell us whether SribeesExpress offers any temperature-controlled
service at all — if not, we'll cap which categories we ship through you, and
that is a decision we need to make now rather than after the first melted
delivery.

## 8. Correcting a booked shipment

Customers mistype phone numbers and give incomplete addresses constantly. The
contract's only post-booking write is `cancel`, and cancel is illegal once
picked up — so a wrong phone number on an in-transit parcel is unfixable
through the API.

**Requested:** `PATCH /ecommerce/shipments/{shipment_id}` accepting
`recipient_phone`, `recipient_address`, `latitude`, `longitude` (and ideally
`requested_delivery_date` from §4), legal until `out_for_delivery`, rejected
with a clear code once it's too late.

Not a blocker — but without it every typo becomes a phone call to your support
desk, which is worse for both of us.

## 9. `recipient_address` as a single string

Our addresses are structured: `address_line1`, `address_line2`, `post_office`,
`district`, `province`, `postal_code`. We'll concatenate them into your single
`recipient_address` string, but:

- **What is the max length?** Not documented. We'll truncate to something safe
  once you tell us — please don't let us discover it via a 422 in production.
- Would you rather receive the structured fields? We have them cleanly and
  they'd likely help your sorting. Accepting an optional structured block
  alongside the string would cost you nothing and improve your data.
- We do **not** currently capture GPS coordinates in the customer app. We can
  add a map pin, but before we build that UI: confirm whether
  `latitude`/`longitude` will actually be used for rider navigation, and
  roughly when. §6 of your doc says they're carried through but unused today.

## 10. Rate limit

60 requests/minute default, and §6 tells us to call `/rates` *"freely on every
checkout page load"*. Those two statements are in tension. A grocery app sees
bursty traffic — payday evenings, promo pushes — and a single customer
re-loading checkout, changing address, and editing their cart fires several
quotes on their own.

We'll cache quotes per (address, weight bucket) and debounce, but please:

- Tell us what ceiling you can give us on a production key.
- Confirm whether the limit is per API key or per account — we'd like separate
  keys per environment without splitting one budget.
- Confirm `429` responses always carry `Retry-After` (§3 says so; just
  confirming it's on every 429, including burst rejections).

## 11. Smaller clarifications

1. **`shipment_id` vs waybill.** §8 says `shipment_id` *is* the waybill id.
   Our schema has separate `courier_shipment_id` and `courier_waybill_number`
   columns inherited from the previous contract. Confirm there is only ever
   one identifier and we'll collapse them.
2. **Quote lifetime vs our checkout.** Quotes expire in 30 minutes. Our COD
   checkout is fast, but a card payment can sit on the bank's 3-D Secure page.
   Confirm the correct pattern is: quote → take payment → book, and re-quote
   plus re-confirm with the customer on `quote_expired`. That is what we've
   implemented; we'd rather validate it than discover it's wrong.
3. **`quote_already_used` vs `quote_expired`.** Both are `409`. Our client
   currently branches on the status code alone. We'll switch to branching on
   `error.code` — please confirm that field is stable and present on **every**
   error response in this domain, including `429` and `401`.
4. **Two coverage maps.** We resolve a fulfilment branch from the customer's
   post office using our own coverage table; you resolve a `city_id` from the
   same post office using yours. These will disagree at the edges — we'll
   accept an order you then can't deliver. Is there a bulk export of your
   serviceable post offices (`GET /ecommerce/coverage`, or a downloadable
   list) we could sync nightly to pre-empt that? Calling `/locations/resolve`
   per address at save time helps, but doesn't catch coverage that changes
   after the address was saved.
5. **COD pricing.** §6 says `cod_amount` and `payment_method` don't affect the
   quote *today*. Since we show the customer a delivery fee before they pay
   and cannot re-bill afterwards, please give us **advance notice** before a
   COD collection fee starts affecting `amount_lkr`.
6. **Timezone.** Examples use `+00:00`. We operate entirely in Asia/Colombo
   (`+05:30`). Confirm all timestamps are ISO-8601 with an explicit offset and
   we'll convert.
7. **Sandbox data.** §11 says sandbox creates real rows. Is there a way to
   clear our sandbox data, and will sandbox shipments ever appear in
   remittances (§3) or invoices?

## 12. What we're building on our side

For context, so you know what to expect from us:

- Rewriting our courier client from the old `/v1/*` contract to
  `/api/v1/ecommerce/*`.
- Calling `POST /ecommerce/locations/resolve` when a customer saves or edits
  an address, caching `city_id` on the address row, and handling all four
  `resolved: false` reasons distinctly in the app UI.
- `POST /ecommerce/rates` at checkout, with `serviceable: false` rendered as a
  normal "we don't deliver here yet" state, not an error.
- `POST /ecommerce/shipments` keyed on our order number
  (`FC-20260828-A7K2M9`, ~18 chars) as `merchant_order_ref` — stable across
  retries.
- A registered HTTPS webhook endpoint with full `X-Sribees-Signature`
  verification, plus a reconciliation poller (which needs §6.2).
- Extending our existing delivery-verification-code feature to COD orders and
  wiring it to whichever option you pick in §1.

**We'd like sandbox keys as soon as they're available** — we can build and
test everything except §1–§3 against the contract as it stands today, and the
answers to those three determine whether we can launch COD at all.
